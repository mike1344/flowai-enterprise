# ADR-009 写操作授权与重复确认令牌

- 状态：**Accepted**
- 日期：2026-11-01
- 决策者：产品/技术负责人（已批准）、实施代理（起草）
- 关联：`docs/03 §4`（重复工单与二次确认）、`docs/04 §3`（创建工单协议细化）、`docs/05 §4`（Agent 流程）、`docs/10 §3-2`；任务 M01-04、M04-03、M04-04
- 冻结边界：不改 `docs/03 §4` 的"重复是风险提示而非禁止"、不改状态机

## 1. 背景

写操作（创建工单）必须同时满足两件**互不等价**的事：
1. **用户已授权这次写操作**（服务端签发，绑定主体/操作/参数）；
2. **疑似重复的风险已被告知并确认**（工业侧签发，绑定候选集合）。

`docs/04 §3` 已明确：重复确认 token **不能代替**操作授权；模型生成的 `confirmed=true` 一律不可信（`docs/05 §5`）。

## 2. 决策：两类令牌严格分离

| 令牌 | 签发方 | 目的 | 绑定 | 时效 | 消费 |
|---|---|---|---|---|---|
| `operation_authorization` | FlowAI API | 证明"该用户在此会话中授权执行该操作及其参数" | `sub`、`sid`、`app_version_id`、`operation`、`params_digest` | **≤300s（默认 120s）** | 一次性，成功创建后标记 `consumed_at` |
| `duplicate_confirmation_token` | Industrial API（`/tickets/precheck`） | 证明"用户已看到这批重复候选并选择继续" | `caller_scope`、`params_digest`、`candidate_set_digest` | **300s**（与 `docs/04 §3` 示例 `expires_in_seconds=300` 一致） | 一次性 |

两者均为**服务端不透明字符串**（`docs/03 §4`："opaque token"），前端只透传，不解析。

## 3. 请求规范化与摘要

`params_digest = SHA-256( canonical(业务字段集合) )`，规则：

1. 只纳入**业务字段**：`device_id`、`fault_id`、`reported_fault_code`、`title`、`description`、`priority`；不含令牌、Trace、时间戳。
2. 规范化：键按字典序；数值统一十进制无前导零；字符串 UTF-8 NFC、去首尾空白、内部连续空白折一；`null` 与字段缺省**视为等价**；布尔小写。
3. `candidate_set_digest = SHA-256( 排序后的候选工单 ticket_no + status )`。
4. 摘要以 hex 存 `idempotency_record.request_hash CHAR(64)`（`docs/03 §1`），**不保存敏感响应**。

## 4. 校验顺序（工业侧，原子事务内）

1. `operation_authorization` 有效（签名/`exp`/`sub` 与 ADR-008 声明一致/未消费）；
2. 业务权限（客户/设备归属、`docs/06 §2`）；
3. 业务状态（客户 `ACTIVE`、设备非 `RETIRED`、故障同设备 → 否则 422）；
4. 重复候选重算（同设备 + 同 `fault_id` 或同规范化 `fault_code`；均缺失时按规范化标题精确匹配；候选仅 `PENDING/IN_PROGRESS/REOPENED`）；
5. 无候选 → 直接创建；有候选且无 `duplicate_confirmation_token` → `409 DUPLICATE_TICKET_CONFIRMATION_REQUIRED`（附候选摘要与新 token）；
6. 有 token → 校验 `params_digest` 与 `candidate_set_digest` **完全一致**；候选集合发生实质变化（新增/关闭候选）→ **409，要求重新预检**；
7. 校验通过 → 创建工单 + `CREATE` 操作记录 + 幂等成功结果 + 两个令牌标记已消费，**同一本地事务**提交。

## 5. 安全规则

- 令牌复用、过期、主体不符、摘要不符 → 安全拒绝（`409`/`422`/`403`），审计记录内部原因，对外不泄露候选细节（`docs/04 §1` 末段）。
- 参数任何变化必须重新确认（`docs/06 §3`"参数变化重确认"）。
- `precheck` **不写工单**、不占用正式创建的幂等键（`docs/04 §3`）。
- 令牌不得出现在 URL、日志、Trace 正文；仅 Authorization 头或 JSON body。
- 重试策略：写请求必须携带稳定 `Idempotency-Key`；超时先按键查询结果，**绝不把超时当作未执行**（`docs/04 §6`）。

## 6. 影响

| 面 | 影响 |
|---|---|
| API | `/tickets/precheck` 返回 `confirmation_token`/`expires_in_seconds`；`/tickets` 接收 `operation_authorization` + 可选 `confirmation_token` |
| 数据 | 令牌消费记录（`token_record` 或复用 `idempotency_record`）；`request_hash` 与候选摘要落库 |
| 测试 | `IND-09`～`IND-14`、`ACC-06`；必须覆盖：未授权写入、确认伪造、过期、候选变化、并发重试 |
| 任务 | M01-04 实现预检/重复/幂等；M04-03 签发操作授权；M04-04 串接两次确认 |

## 7. 复审条件

- 令牌需要跨实例共享消费状态时（多副本）；
- 需要支持"批量创建工单"（当前不支持，属范围外）；
- `docs/03 §4` 的重复判定规则变更（须先走 CR）。
