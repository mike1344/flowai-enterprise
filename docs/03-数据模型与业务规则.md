# 03 数据模型、约束与工业业务规则

> Industrial 独立 MySQL 数据库；表名/类型是实施建议，迁移前必须保持 OpenAPI 与业务规则一致。主键 BIGINT；时间 UTC DATETIME(6)，对外 ISO8601 带时区；字符集 utf8mb4。外键使用 RESTRICT，不级联删除业务历史。

## 1. Industrial 核心实体字段
| 表 | 字段（建议类型） | 约束/说明 |
|---|---|---|
| customer | id BIGINT; customer_code VARCHAR(32); customer_name VARCHAR(150); contact_name VARCHAR(60); contact_phone VARCHAR(30)?; contact_email VARCHAR(120)?; service_level VARCHAR(20); status VARCHAR(20); address VARCHAR(255)?; created_at/updated_at DATETIME(6) | PK(id), UNIQUE(customer_code), name/contact 非空；service_level=STANDARD/PRIORITY；status=ACTIVE/INACTIVE；停用后不可新建普通工单 |
| product_model | id; model_code VARCHAR(40); model_name VARCHAR(120); category VARCHAR(60); manufacturer VARCHAR(120); specification JSON?; warranty_months SMALLINT; status; timestamps | UNIQUE(model_code)；warranty_months 0..120；status=ACTIVE/DISCONTINUED；停产型号历史仍可维修 |
| device | id; device_code VARCHAR(40); serial_number VARCHAR(80); model_id; customer_id; installation_date DATE?; warranty_start_date DATE?; warranty_end_date DATE?; location VARCHAR(255)?; status; timestamps | UNIQUE(device_code), UNIQUE(serial_number), FK(model_id,customer_id)；保修日期同空或同非空且 end>=start；status=ACTIVE/MAINTENANCE/RETIRED；退役不可新建普通工单 |
| fault_record | id; fault_no VARCHAR(40); device_id; fault_code VARCHAR(40)?; title VARCHAR(150); description TEXT; severity; occurred_at; reported_by_ref VARCHAR(100)?; source; created_at | UNIQUE(fault_no), FK(device_id)；severity=LOW/MEDIUM/HIGH/CRITICAL；source=MANUAL/AGENT/SYSTEM；故障可独立存在 |
| repair_ticket | id; ticket_no VARCHAR(40); customer_id; device_id; fault_id NULL; title VARCHAR(150); description TEXT; reported_fault_code VARCHAR(40)?; priority; status; assignee_id NULL; source; requester_ref VARCHAR(100); resolution TEXT?; version INT; created_at/updated_at; resolved_at?; closed_at? | UNIQUE(ticket_no); FK(customer,device,fault?,assignee?)；customer 必须等于设备归属；fault 非空必须同设备；priority=LOW/NORMAL/HIGH/URGENT；status=PENDING/IN_PROGRESS/RESOLVED/CLOSED/REOPENED；version>=1 |
| ticket_action | id; ticket_id; action_type; actor_type; actor_ref; initiated_by_ref?; old_status?; new_status?; details JSON?; comment TEXT?; trace_id?; created_at | FK(ticket_id)；关键变更 append-only；动作 CREATE/ASSIGN/STATUS_CHANGE/LINK_FAULT/COMMENT；写入同事务 |
| service_user | id; staff_code VARCHAR(40); display_name VARCHAR(80); department VARCHAR(80)?; status; timestamps | UNIQUE(staff_code)；status=ACTIVE/INACTIVE；只有 ACTIVE 可接受新分配 |
| service_identity_binding | id; identity_provider VARCHAR(40); external_user_id VARCHAR(100); service_user_id?; customer_id?; business_role; status; created_at | UNIQUE(identity_provider,external_user_id)；business_role=CUSTOMER_USER/SERVICE_STAFF/SERVICE_ADMIN；status=ACTIVE/REVOKED；客户/服务人员绑定符合角色要求 |
| idempotency_record | id; operation; caller_scope; idempotency_key; request_hash CHAR(64); status; response_status?; response_body JSON?; resource_type?; resource_id?; created_at; expires_at | UNIQUE(caller_scope,operation,idempotency_key)；status=PROCESSING/SUCCEEDED/FAILED；默认 24h（可配置）；不得保存敏感响应 |

所有 `?` 表示可空；除明确可空字段外均 NOT NULL；所有业务代码字段非空白，字符串长度及格式由 API 校验。数据库 CHECK、FK、UNIQUE 与应用层校验同时使用；跨表一致性（如工单 customer=device.customer）在事务内校验，不能仅靠普通 FK 推断。

## 2. 关系与索引
- Customer 1:N Device；ProductModel 1:N Device；Device 1:N FaultRecord；Device 1:N RepairTicket；Customer 1:N RepairTicket。
- FaultRecord 1:N RepairTicket（ticket.fault_id 可空）；ServiceUser 1:N RepairTicket（assignee 可空）；RepairTicket 1:N TicketAction。
- 建议索引：device(customer_id,status)、fault_record(device_id,occurred_at)、repair_ticket(customer_id,status,created_at)、repair_ticket(device_id,status,created_at)、repair_ticket(assignee_id,status)、ticket_action(ticket_id,created_at,id)、idempotency_record(expires_at)。
- 第一版不支持设备客户归属转让；如后续增加转让，须先设计历史归属快照与访问权限迁移。

## 3. 工单状态机
`PENDING -> IN_PROGRESS -> RESOLVED -> CLOSED`；`RESOLVED -> REOPENED`、`CLOSED -> REOPENED`、`REOPENED -> IN_PROGRESS`。其他转移一律拒绝。
- 新建必为 PENDING；进入 IN_PROGRESS 前必须分配 ACTIVE ServiceUser。
- IN_PROGRESS -> RESOLVED 必须有非空 resolution，设置 resolved_at。
- RESOLVED -> CLOSED 需授权关闭，设置 closed_at。
- REOPENED 必须填写原因；重开后保留既往关闭/解决操作历史，时间字段语义需在实现前用 ADR 确认（推荐保留最近一次时间 + 操作历史完整记录）。
- 分配与状态改变是两次独立操作；关闭工单不能修改故障关联；所有变更使用 version 乐观锁。

## 4. 重复工单与二次确认
P0 可解释判定：同设备 + 同 fault_id 或同规范化 fault_code；两者均缺失时可按规范化标题精确匹配；候选工单状态仅 PENDING/IN_PROGRESS/REOPENED。重复为**风险提示**，不直接禁止创建。
- `POST /tickets/precheck` 先校验权限、设备/客户/故障、重复候选；返回需要确认的候选摘要与短期、绑定主体/请求摘要/候选集合的 opaque token；不写工单。
- 用户确认后 `POST /tickets` 携带服务端可验证的操作授权与重复确认 token；重新校验授权、设备状态、重复候选，实质变化需重新确认。
- Agent 的普通写操作确认与疑似重复二次确认是不同的 UI/状态；不能用模型生成的 `confirmed=true` 代替服务端确认。

## 5. 一致性与并发
- 创建工单 + CREATE 操作历史 + 幂等成功结果在一个本地事务提交；失败全回滚。
- 状态变更 + version 自增 + 时间戳 + STATUS_CHANGE 操作历史同事务；使用版本条件更新，0 行更新返回 409。
- 幂等唯一键由 DB 强制；相同键同请求返回原资源；同键不同摘要 409；处理中 409/重试建议；服务崩溃需基于已提交资源恢复，不能重复创建。
- FlowAI 与 Industrial 不使用分布式数据库事务；网络响应丢失时按同一幂等键查询/安全重试。

## 6. FlowAI 数据模型概要（实施时单独迁移）
User, Role, Permission, UserRole, ResourceGrant, ModelConfig（仅密钥引用）, AIApplication, ApplicationVersion（不可变配置快照）, ApplicationKnowledgeBase, KnowledgeBase, Document, DocumentVersion, DocumentChunk, IndexVersion, ToolDefinition, ApplicationTool, Conversation, Message, AgentExecution, ToolExecution, AuditLog。
- 多应用:多知识库 M:N；多应用:多工具 M:N；文档和索引按知识库与版本隔离；会话绑定已发布应用版本。
- 仅 P1 要求索引版本历史与回滚、完整发布回滚；P0 仍需保留当前已就绪索引与构建中索引的安全切换语义。
