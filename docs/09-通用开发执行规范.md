# 09 通用项目开发执行规范

## 1. 总原则
此文档包是当前需求基线；任何执行者均不能凭空宣称某任务已实现。先阅读 README 和相关章节，再检查仓库实际状态。每次只推进一个任务 ID，先确认依赖满足，遵循最小改动原则。

## 2. 每轮执行工作流
1. **READ**：读取任务 ID、需求映射、前置依赖、现有代码、测试和 ADR。
2. **PLAN**：输出本轮范围、将改动文件、数据库迁移影响、接口兼容影响、风险与验收方法；歧义先提问。
3. **IMPLEMENT**：只写当前任务所需代码，不提前实现未授权 P1，不使用硬编码假数据冒充业务结果。
4. **TEST**：运行本任务单测/集成/契约/安全用例，报告命令、实际结果、失败原因；环境缺失时标明 NOT RUN，不能声称 PASS。
5. **REVIEW**：检查 RBAC、业务授权、输入校验、幂等、日志脱敏、数据库迁移和回滚影响。
6. **REPORT**：更新任务状态、OpenAPI/ADR/文档，给出变更摘要、测试证据、未完成项与下一任务建议。

## 3. 禁止事项
- 禁止跳过权限、事务、幂等与错误处理，禁止直接跨库访问。
- 禁止 Agent 直接执行任意 SQL/shell/URL、控制工业硬件或信任模型输出的授权字段。
- 禁止真实密钥入库/入仓库、敏感数据原样日志、输出模型内部推理链。
- 禁止未经批准重构无关模块、修改冻结业务规则、添加多租户/K8s/拖拽工作流。
- 禁止仅凭页面显示“成功”认定数据库写入成功；禁止将模拟数据描述成真实客户数据。
- 禁止删除失败测试、放宽权限断言或事后调整验收标准以取得通过。

## 4. 任务完成定义（DoD）
- 需求/接口/数据变更一致；自动化测试覆盖正常、边界、错误、权限；迁移可在干净数据库重放；文档和 OpenAPI 更新；运行日志不泄密；关键操作 Trace 可追踪；任务报告含真实测试结果。
- 前端任务必须连接真实 API，覆盖加载/空/错误/未授权状态；后端任务需含 DB 约束和 API 层校验；跨服务任务需含网络超时与幂等恢复。

## 5. 任务交付报告格式
```text

```

## 6. 阻塞问题处理
发现需求矛盾时，列出冲突章节、业务影响、推荐选项，等待确认；更新 `10-需求追踪与决策.md` 的 ADR 后再实施。若已有项目代码与冻结设计冲突，先给出兼容/迁移方案，不能擅自覆盖。

## 7. 第一轮指令
“执行 M00-01：审计现有仓库结构、已实现功能、依赖版本、运行方式、数据库与 Docker 现状。输出差异表、风险和最小重构建议；**本轮不修改任何项目代码**，只允许新增审计报告与 ADR 草稿。待确认后执行 M00-02。”

## 8. 执行主体与交接
- 执行者可以是开发人员、外包团队、Codex、Cursor、Trae、Claude Code 或其他工具；项目任务编号、交付物、测试与验收标准不因工具改变。
- 执行者不拥有自行修改冻结需求的权限；产品负责人审批范围和优先级，技术负责人审批架构/接口/迁移，测试负责人依据证据确认验收。个人项目允许一人兼任，但各项审批和验证结果仍需记录。
- 每次交接提供：当前任务编号、分支/提交标识、已修改文件、迁移状态、运行命令、测试证据、环境依赖、阻塞问题、下一步。不得仅依赖聊天记录交接。
- 状态定义：TODO 未开始；READY 依赖满足；DOING 实施中；BLOCKED 阻塞；REVIEW 待审查；TESTED 已通过测试；DONE 验收完成。DONE 必须有测试证据及验收记录。

## 10. 质量门禁与例外
- 开始门禁：依赖满足、需求清楚、必要的接口/数据契约已确认。
- 合并门禁：变更经审查、自动化测试实际运行、重要安全检查通过、迁移方案可追溯。
- 验收门禁：验收人核对测试证据与业务结果，更新需求追踪矩阵；未运行测试不得标记通过。
- 例外与阻塞须记录原因、影响、批准人和补救任务，不得静默跳过。

## 11. 进度更新的强制步骤
- 任务开始前在 `progress/进度看板.html` 设置负责人、状态和备注。
- 任务结束后先提供实际测试证据，再把状态设为 DONE；导出 `progress/任务进度.json` 并提交版本库。
- 任何执行者必须先读取进度 JSON；不得依据聊天内容推测任务已完成。
- Gate 放行必须由对应任务全部 DONE 决定；看板百分比不替代验收。
